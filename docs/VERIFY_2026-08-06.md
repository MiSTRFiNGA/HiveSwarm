## 3. dropWeight math — independent re-derivation

Old code (`git show da3bb54^:index.html:207-212`):
```js
function maybeDropWeapon(x,y,elite){
  ...
  const pool=(EDIT.weapons||[]).filter(w=>w&&w.id);if(!pool.length)return;
  const w=pool[Math.floor(Math.random()*pool.length)];
  ...
```
This is `Math.floor(rand*N)` over the full pool — genuinely uniform, every weapon (toxic included) at `1/7`. Confirms the commit message's claim that toxic was never over-weighted pre-fix.

New code (`index.html:226-235`):
```js
const total=pool.reduce((s,w)=>s+Math.max(0,w.dropWeight??1),0)||pool.length;
let roll=Math.random()*total,w=pool[pool.length-1];
for(const cand of pool){const wt=Math.max(0,cand.dropWeight??1);if(roll<wt){w=cand;break}roll-=wt}
```
- Negative weights are clamped to 0 via `Math.max(0,...)` — can't go negative and skew `total`.
- `total===0` (all weights zeroed) is guarded by `||pool.length`, so `roll` is still bounded and the loop safely falls through to the `pool[pool.length-1]` default instead of throwing/hanging.
- Standard weighted-pick loop, no off-by-one: `roll` is decremented by each candidate's own weight and compared with `<`, so the last candidate is only reached if all prior weights were exhausted — correct semantics, matches `pool[pool.length-1]` fallback for float rounding at the boundary.
- All 7 weapons ship with `dropWeight:1` (`index.html:69-78`), so behavior is unchanged by default (still uniform); the field is present in `fields()`-rendered numeric inputs so it now shows and is tunable in FORGE → WEAPONS.

Claim B **CONFIRMED** on both halves (uniform-before, correctly-weighted-after).

## 5. FORGE UI editability trace

`fields(obj,path)` (`index.html:715`):
```js
function fields(obj,path){return Object.entries(obj)
  .filter(([,v])=>typeof v==='number'||typeof v==='string')
  .map(([k,v])=>`<label>${k}<input data-p="${path}.${k}" value="${v}" ...></label>`).join('')}
```
Only picks `number`/`string` typed values — arrays and nested objects are silently skipped.

- **`dropWeight` (claim B):** numeric field on each weapon object. WEAPONS tab (`tab===2`, `index.html:745`) calls `fields(w,'weapons.'+i)` per weapon → `dropWeight` shows up automatically as an editable numeric input alongside damage/rate/etc. **Fully FORGE-editable, confirmed.**

- **`stages` (claim C):** `FORGE_BASE.stages` is an **array of objects** (`id,name,seconds,enemyCap,bg,bossMul`). `TABS` (`index.html:710`) = `['ENTITIES','PLAYER','WEAPONS','WAVES','WORLD','SPRITES','AUDIO','DATA','BEASTIARY']` — there is **no STAGES tab**, and no existing tab's `fields()` call reads `EDIT.stages` (WAVES tab only renders `fields(EDIT.waves,...)`, WORLD only `fields(EDIT.world,...)`). Because `fields()` filters out array-typed values, even a naive `fields(EDIT,'')` call would not expose it. The **only** way to change stage data in the running app is the DATA tab (`tab===7`) EXPORT/IMPORT JSON pack round-trip, which serializes all of `EDIT` (including `stages`) — confirmed via `forgeMerge()` id-keyed array merge logic (`index.html:92`), which does correctly merge saved `stages` rows back onto the shipped defaults by `id`. So round-trip through `forgeMerge()`/localStorage **works** (claim C's persistence half is solid), but stages are **NOT directly editable in the live FORGE UI** — only via hand-editing the exported JSON and re-importing. This falls short of "FORGE-editable" in the everyday in-app-slider sense the owner asked for.

**Action needed if the owner wants true in-UI stage editing:** add a `STAGES` tab (or extend `WAVES`) with a small per-stage editor (loop `EDIT.stages` similar to the WEAPONS tab's per-weapon `article` blocks, since `bg` is a 2-element string array and would need a small custom control rather than plain `fields()`).
